# Decision Log

Chronological record of decisions made during Phase 0/1 planning. Each
non-trivial decision also has a full ADR in `docs/adr/`.

| # | Decision | Rationale (short) | ADR |
|---|---|---|---|
| 1 | AI Director (LLM) and Video Engine are fully separate layers, communicating only via versioned JSON schemas | The entire point of the project: either side must be replaceable without rewriting the other | [0001](adr/0001-director-engine-separation.md) |
| 2 | `IVideoEngine` (which model) and `IComputeProvider` (where it runs) are two separate interfaces, not one | GPU hosting strategy and model choice are independent axes of change | [0002](adr/0002-compute-provider-abstraction.md) |
| 3 | Backend language: Python (FastAPI) across every service | Wan2.1 and its successors are PyTorch; one language end-to-end removes an unnecessary serialization/FFI boundary | [0003](adr/0003-language-python.md) |
| 4 | Workflow engine: Temporal.io, isolated behind Render Orchestrator | Durable execution, retries, and a human-approval signal (storyboard gate) are native to Temporal; isolating it keeps a future swap possible | [0004](adr/0004-workflow-engine-temporal.md) |
| 5 | GPU compute: start on RunPod Serverless + rented Vast.ai instances, not Kubernetes | Lowest cost/complexity for early experiments; Kubernetes is deferred to Phase 7 behind `IComputeProvider` | [0005](adr/0005-gpu-provider-runpod-vastai-first.md) |
| 6 | First Video Engine: Wan2.1 (Apache-2.0), wrapped in `Wan21Adapter` | Supports T2V/I2V/video-edit, runs on consumer/prosumer GPUs, permissive license | (tracked in `models/registry.yaml`) |
| 7 | Repository: `sallehly-ai-video-engine`, fully separate from `sallehly_app` | Independent product, not a feature of the existing Flutter app | — |
| 8 | License for this repository's own code: **not yet decided** | Needs a deliberate choice (MIT/Apache-2.0/proprietary) — flagged for user decision, not assumed | — |
| 9 | Structured output enforcement = Claude forced tool-use + a provider-agnostic `RetryingLLMProvider` decorator | Retry/validation should not be reimplemented per provider; a decorator applies to any `ILLMProvider` uniformly | [0006](adr/0006-structured-output-retry-decorator.md) |
| 10 | Creative Brief Parser and Story Planner are separate services from the Creative Director orchestrator, each with their own `ILLMProvider` dependency and prompt template | Keeps each LLM call and each prompt template independently focused, versioned, and retriable | (see `services/ai-director/README.md`) |
| 11 | Storyboard Generator runs after Shot Planner, not before Scene Generator as originally listed in Phase 1 planning; "Director"/"Engine" naming reconciled | Storyboard frames reference shot ids that don't exist until shots are planned; this is also the cheapest point for the human approval gate | [0007](adr/0007-pipeline-stage-terminology-and-ordering.md) |
| 12 | Storyboard Generator moved again: now runs *after* Camera/Motion/Lighting/Style planning, not before | Phase 2 storyboard frames must describe lens/movement/lighting, which don't exist until those Directors run; this supersedes ADR 0007's ordering (not its terminology mapping) | [0008](adr/0008-storyboard-after-technical-planning.md) |
| 13 | Two approval gates, not one: storyboard (gate 1) and `render_plan.schema.json` (gate 2) | Gate 1 catches a wrong creative/shot plan; gate 2 catches anything specific to the engine-compiled RenderSpecs (e.g. a shot split for exceeding `max_shot_duration_sec`) before any GPU cost is spent | [0008](adr/0008-storyboard-after-technical-planning.md) |
| 14 | Camera/Motion/Lighting/Style Directors and the Render Specification Generator are all deterministic (no LLM call) | Their job is mechanical translation of already-decided creative intent (from the Story Planner) into cinematography/technical parameters - a good fit for rule-based logic, consistent with Scene Generator/Shot Planner's Phase 1 precedent | (see each service's own README) |
| 15 | Prompt composition for `positive_prompt`/`negative_prompt` is currently inline in Render Config Compiler | A dedicated Prompt Builder (prompt-fragment library, per-engine phrasing dialects) wasn't part of Phase 2's scope; a simple deterministic concatenation is enough to produce valid, useful RenderSpecs today | (see `services/render-config-compiler/README.md`) |
| 16 | `GenerationPipeline` (`services/render-orchestrator`) is the sole place a `RenderSpec` dict becomes a concrete engine call | Keeps `CreativeDirector`/`CreativeCompiler` unaware Wan2.1 (or any engine) exists, per ADR 0001; this is where the dict->dataclass `RenderSpec` conversion lives | [0009](adr/0009-generation-pipeline.md) |
| 17 | `GenerationJob` status names (`queued`/`running`/`completed`/`failed`) are distinct from `ComputeJobStatus`'s (`.../succeeded`/`.../cancelled`) | A `GenerationJob` is the platform's business object; `ComputeJobStatus` is a specific compute provider's report - `GenerationPipeline` maps one to the other rather than reusing the same enum for both | [0009](adr/0009-generation-pipeline.md) |
| 18 | RunPod prioritized as the first production-ready `IComputeProvider`; `VastAIProvider` stays a stub | Vast.ai's rented-instance model needs a companion self-hosted job-runner service (`infra/vastai/`) not yet built; RunPod's request/response Serverless API was simpler to productionize first | (see `services/video-engine-adapter/README.md`) |
| 19 | `IStorageProvider` (`packages/storage-sdk`) is separate from `AssetManager`'s registry, and isn't on the Phase 3 critical path | A `RawClip`'s URI already points somewhere valid (compute provider's upload target); `IStorageProvider` is for the platform copying/persisting bytes it owns, needed starting Phase 5 (correctly predicted here, though for reference-image uploads rather than Post-Processing - see `POST /assets/upload`, [0011](adr/0011-frontend-and-auth.md)), not Phase 3 | [0009](adr/0009-generation-pipeline.md) |
| 20 | Only `Project` gets a new persistence store; DirectorPlan/Storyboard/RenderSpec/GenerationJob/Asset reuse `IDirectorMemoryStore`/`IGenerationJobStore`/`AssetManager` from Phases 1-3 | Building three more repositories would duplicate working, already-tested stores that follow the exact same interface-based pattern | [0010](adr/0010-persistence-and-lifecycle.md) |
| 21 | `ProjectLifecycle` is the one place the full create-project-to-generated-video logic lives; both `SyncProjectOrchestrator` (used today) and the Temporal workflow's activities call it, neither reimplements it | Avoids duplicating business logic between a durable (Temporal) and non-durable (synchronous) driver of the same flow | [0010](adr/0010-persistence-and-lifecycle.md) |
| 22 | `apps/api` depends on `IProjectOrchestrator`, not `ProjectLifecycle` or Temporal directly | A future `TemporalProjectOrchestrator` (start/signal a real workflow) implements the same interface `SyncProjectOrchestrator` does today - route handlers won't change when that swap happens | [0010](adr/0010-persistence-and-lifecycle.md) |
| 23 | Real `temporalio` workflow/activity code is written and structurally validated, but not executed end-to-end in this environment | The ephemeral test server needs a binary download blocked by this sandbox's network policy - same class of limitation as Phase 3's live GPU inference | [0010](adr/0010-persistence-and-lifecycle.md) |
| 24 | `LocalHeuristicLLMProvider` (keyword/regex `CreativeBrief`/`StoryOutline` stubs, zero network) is `apps/api`'s default `ILLMProvider` | Unlike `FakeLLMProvider`'s fixed scripted responses, this answers *arbitrary* requests - required for a running API server to be testable end-to-end without a live Claude account | [0010](adr/0010-persistence-and-lifecycle.md) |
| 25 | Rejecting a storyboard/render-plan stage immediately regenerates it, rather than requiring a separate "regenerate" call | Simpler for API consumers; "reject with feedback" and "regenerate" were never going to be used independently | [0010](adr/0010-persistence-and-lifecycle.md) |
| 26 | `packages/auth`: `IUserStore` + `IAuthProvider`, `LocalAuthProvider` (PBKDF2 password hashing, opaque bearer tokens) as the default implementation | Same interface-swap pattern as every other provider (`ILLMProvider`, `IVideoEngine`, `IComputeProvider`) - `apps/api` never depends on hashing/token-storage details | [0011](adr/0011-frontend-and-auth.md) |
| 27 | Every user gets one personal default workspace (`ws_<user_id>`) at registration; no team/workspace-membership model yet | Satisfies "prepare: users, projects ownership, permissions" via real, enforced, testable ownership checks at the scope Phase 5 needs; a membership model is additive later, not a rewrite | [0011](adr/0011-frontend-and-auth.md) |
| 28 | `GET /projects/{id}/plan`, `/storyboard`, `/render-plan` added to `apps/api` | Building the frontend's storyboard/render-plan review screens against the existing contract surfaced that Phase 4 only exposed approve/reject actions, never the artifact content a human needs to see before deciding - backed by `IDirectorMemoryStore`, which already held this data since Phase 1 | [0011](adr/0011-frontend-and-auth.md) |
| 29 | `apps/api` gets a `CORSMiddleware` + `Settings.cors_allowed_origins` | Running the real frontend in a real browser (not `TestClient`) revealed every cross-origin request was blocked - a bug class invisible to `httpx.TestClient`-based tests no matter how thorough | [0011](adr/0011-frontend-and-auth.md) |
| 30 | `POST /projects/{id}/retry-generation` and `POST /assets/upload` added | Completes the real-time job status "retry option" and the reference-image upload flow the Phase 5 spec calls for; `retry_generation` shares `ProjectLifecycle._run_generation` with `generate_video` rather than duplicating job-submission logic | [0011](adr/0011-frontend-and-auth.md) |
| 31 | `apps/web-dashboard`: Next.js 16 (App Router) + TypeScript + Tailwind v4, talking to `apps/api` only through a typed `apiClient.ts` | "Do not bypass the backend" - every route the frontend calls exists in `docs/api/openapi.yaml`; no route was added speculatively | [0011](adr/0011-frontend-and-auth.md) |
| 32 | `packages/video-composition-sdk` (`IRenderCompositor`, `ITransitionPlugin`, `IUpscaler`) mirrors `video-engine-sdk`'s role for post-production; `config_sdk.TRANSITION_PLUGIN_REGISTRY` reuses the same `Registry` class every other provider registry uses | Post-production is an independent axis of change from generation - a real plugin architecture (register a class, look it up by key), not a special case bolted onto the generation-era types | [0012](adr/0012-post-production-pipeline.md) |
| 33 | Post-production is tested with real ffmpeg subprocess execution against real synthetic clips (`tests/media_helpers.py`), not mocked | Unlike GPU inference or a live Temporal server, `ffmpeg` is a real, installable, executable dependency in this environment (`apt-get install ffmpeg`, confirmed to include libx264/libvpx/libopus/libass) - holding this phase to a higher, actually-executed bar than earlier not-yet-executable boundaries | [0012](adr/0012-post-production-pipeline.md) |
| 34 | A hard cut always uses ffmpeg's `concat` filter, never a zero-duration `xfade` | `xfade`'s `offset` equal to the first input's full duration was found (empirically) to collapse the output almost entirely - `concat` sidesteps the bug and is the semantically correct operation for a real cut anyway | [0012](adr/0012-post-production-pipeline.md) |
| 35 | `match_cut` and `whip_pan` transition plugins are documented approximations (a very short plain fade; ffmpeg's `hblur` xfade preset), not simulations of true match cuts/camera pans | Both need per-shot visual alignment data the pipeline doesn't produce today - approximating honestly (with a docstring saying so) rather than overclaiming a content-aware effect | [0012](adr/0012-post-production-pipeline.md) |
| 36 | `IUpscaler`/`PassthroughUpscaler` (copies input unchanged) is the only concrete upscaling implementation | Explicitly scoped as "prepare interfaces for" upscaling/frame interpolation, not implement - real upscaling needs a GPU model deployment, the same class of limitation as Wan2.1 inference | [0012](adr/0012-post-production-pipeline.md) |
| 37 | `BrandingPackage.intro_asset_id`/`outro_asset_id` become real `Timeline.video_clips` entries (`WatermarkEngine.with_intro`/`with_outro`); only `logo_asset_id` stays an overlay `FfmpegCompositor` applies directly | Reuses the exact same `concat`/`xfade` transition machinery every other clip uses instead of a parallel "branding clip" code path | [0012](adr/0012-post-production-pipeline.md) |
| 38 | Post-production (services/post-processing, services/export-service) is not wired into `ProjectLifecycle`/`apps/api`/`apps/web-dashboard` yet | Phase 6's scope was the post-production modules and their tests; lifecycle/API/frontend integration is the natural next phase, same relationship Phase 4 (pipeline) had to Phase 5 (product layer on top of it) | [0012](adr/0012-post-production-pipeline.md) |
| 39 | `packages/cinematic-intelligence-sdk` + `services/cinematic-intelligence` is a third independent-axis contract package, alongside `video-engine-sdk` (generation) and `video-composition-sdk` (post-production); three new `config_sdk.Registry` instances (`PROMPT_TRANSLATOR_REGISTRY`, `QUALITY_METRIC_REGISTRY`, `REPAIR_STRATEGY_REGISTRY`) reuse the same plugin mechanism as `TRANSITION_PLUGIN_REGISTRY` | A continuity-rule change should never touch, or even import, ffmpeg- or engine-related code; extension points are real plugin registries, not if/elif chains | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 40 | `CharacterIdentityProfile`/`StyleLock` are immutable once created (`locked: true`, schema `const`); `ObjectProfile`/`EnvironmentProfile` intentionally allow state (location history, damage state, weather/time-of-day via `update()`) to evolve | "Generate immutable Character Identity Profiles... never regenerate identity, only reuse" is the literal Phase 7 requirement; objects/environments are allowed to change deliberately, which is exactly what distinguishes an intentional change from a continuity violation | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 41 | Scene/Camera Continuity Engines compare two adjacent shots' plain-dict continuity state via fixed compatibility tables (180-degree-rule entry/exit pairing, opposite-movement pairs, angle/shot-type rank distance), not a vision model | Every violation has a concrete, deterministic, testable trigger condition - legible and debuggable in a way a similarity score from an embedding model wouldn't be, and buildable without a vision model this sandbox doesn't have | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 42 | `QualityReport.embeddings_used` is a schema-level `const: false`; every built-in `IQualityMetric` scores from already-computed `ContinuityReport`/`StyleLock`/`PromptPackage.score` violations via a fixed severity-to-penalty table | Makes "this is not model-based" a checkable fact on the wire, not just a docstring claim; `IEmbeddingProvider` (CLIP/DINO) is prepared, not implemented, for the same reason `IUpscaler` (ADR 0012) and real GPU inference are - needs a deployed model this sandbox doesn't have, and Phase 7 explicitly forbids training one | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 43 | `AutomaticRepairEngine` routes a `QualityReport`'s single worst-scoring dimension to one `IRepairStrategy`, always scoped to the report's own shot_id; strategies with nothing to act on return `status="failed"` rather than fabricating a fix | "If quality drops, repair only the affected shot" is the literal requirement; a real, tested failure path (not just a happy path) when a strategy lacks the context it needs | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 44 | `IGraphStore`'s only concrete implementation is `InMemoryGraphStore`; `DirectorMemoryGraph` uses deterministic node ids (`node_<type>_<ref_id>`) so re-recording a subject is idempotent | Same swap-point discipline as `IProjectStore` (`packages/persistence`) - a real graph database (Neo4j or similar) is a later implementation behind the same interface, not a rewrite | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 45 | `ReferenceImageEngine`/`IReferenceConditioningAdapter`: real `ReferencePackage`s are built, but `prepared_for.controlnet`/`ip_adapter` default false and no generation-time conditioning runs | Needs an engine/adapter combination this codebase doesn't have; the interface documents the future integration point without changing `RenderSpec`'s shape today | [0013](adr/0013-cinematic-intelligence-layer.md) |
| 46 | `CinematicIntelligenceCoordinator` is the one place anything outside `services/cinematic-intelligence` reaches any of the ten Phase 7 engines | A single integration point means a future caller (a second orchestrator, a CLI) gets the same guarantees `ProjectLifecycle` does, through the same six methods, rather than each caller reaching into individual engines | [0014](adr/0014-pipeline-integration.md) |
| 47 | Cinematic Intelligence enrichment runs at render-plan-compile time (inside `approve_storyboard`/`reject_render_plan`), not after `GenerationJob` completion as ADR 0013's Consequences speculated | Every `RenderSpec` a human reviews at gate 2 already carries CIL-built prompts and recorded continuity violations, before any GPU cost is spent; `QualityReport.embeddings_used: false` (ADR 0013) still holds, just earlier in the flow | [0014](adr/0014-pipeline-integration.md) |

| 49 | `PostProductionRunner` (`services/render-orchestrator`) reuses every Phase 6 module (`TimelineBuilder`/`FfmpegCompositor`/`ExportService`/`AssetPackager`) unchanged, bridging `GenerationPipeline`'s `AssetManager` records into it | Phase 6 was already real and tested; the integration gap was purely "nothing calls it yet," not a missing capability | [0014](adr/0014-pipeline-integration.md) |
| 50 | `apps/api/state.py`'s hardcoded `Wan21Adapter()` construction is replaced with `VIDEO_ENGINE_REGISTRY.create(settings.video_engine)`; `SallehlyModelAdapter` registered as `sallehly-v1` proves the swap | `VIDEO_ENGINE_REGISTRY`/`Settings.video_engine` already existed (ADR 0009) but were never actually read by `apps/api` - a real gap, found while implementing config-driven engine swapping, not a hypothetical one | [0014](adr/0014-pipeline-integration.md) |
| 51 | `IEmbeddingProvider` (`ClipEmbeddingProvider`/`DinoEmbeddingProvider`) and `IReferenceConditioningAdapter` (`ControlNetConditioningAdapter`/`IPAdapterConditioningAdapter`) lazily import their real ML dependency and raise `ModelUnavailableError` when it's missing, except `ControlNetConditioningAdapter`'s default `preprocessor="canny"`, which runs genuine Pillow edge detection | Cosine similarity and classical Canny edge detection need no trained model and are fully real in this sandbox; everything that genuinely needs `torch`/`open_clip`/`torchvision`/`controlnet_aux`/`transformers` (none installed here) fails loudly and actionably instead of faking a result | [0014](adr/0014-pipeline-integration.md) |

## Open decision: repository license

Every dependency this project vendors or wraps (Wan2.1: Apache-2.0) is
tracked in `models/registry.yaml`, but the license for *this repository's
own code* has not been set — no `LICENSE` file is included yet. This is
deliberately left to you: it affects whether the platform itself can be
open-sourced, and picking wrong is hard to undo once external
contributors or customers are depending on a license grant. Decide when
ready and this doc will be updated with the ADR.
